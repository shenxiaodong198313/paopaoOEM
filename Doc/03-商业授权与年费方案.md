# 商业授权与年费方案

## 目标

- 对标准 OEM 厂家提供方便集成的授权方式
- 支持“按用户/年”收费
- 统计口径尽量准确，同时避免给客户接入造成很高负担
- 能够远程停用、续费、升级和调整功能包

## 推荐结论

- 推荐采用“厂家主合同 + 年度席位包 + 在线 License”模式
- 不建议只按 APK 包名做一次性授权
- 也不建议完全依赖客户端本地计数，容易被绕过

## 推荐计费对象

- 合同主体：厂家客户
- 计费单元：年付席位
- 统计口径：年度内的有效活跃用户数或活跃设备数
- 核心建议：默认按“年活跃设备席位”计费，比按账号更容易准确落地

## 为什么优先按设备席位

- 很多 OEM 宿主不一定有统一账号体系
- 同一设备对应一个输入法安装实例，统计更稳定
- 厂家对设备口径更容易接受和核对
- 比“用户账号数”更少依赖客户的内部系统配合

## 如果坚持按用户/年收费

- 推荐让厂家宿主在初始化时传入其业务用户 ID 的脱敏哈希值
- SDK 不保存明文用户 ID，只保存：
- `customerId`
- `userHash`
- `deviceHash`
- `packageName`
- `sdkVersion`

## 推荐统计模型

- 主统计口径：去重后的 `userHash`
- 兜底统计口径：去重后的 `deviceHash`
- 对账口径：按月沉淀一次“月活唯一用户数”和“月活唯一设备数”
- 年度收费时，按合同约定取：
- 年峰值 MAU
- 或年度去重用户数
- 或购买席位上限

## 推荐授权流程

1. 为每个厂家分配 `customerId` 与 `appKey`
2. 厂家宿主初始化 SDK 时上报签名摘要和应用包名
3. License Server 返回签名 License Token
4. SDK 本地验签并缓存 License
5. SDK 定时上报活跃统计和授权心跳
6. 服务端根据席位和合同状态决定是否续发 License

## 推荐 License 字段

- `customerId`
- `licenseId`
- `packageName`
- `certSha256`
- `issuedAt`
- `expireAt`
- `gracePeriodDays`
- `featureFlags`
- `seatLimit`
- `billingMetric`
- `environment`

## 推荐统计上报字段

- `customerId`
- `licenseId`
- `packageName`
- `certSha256`
- `sdkVersion`
- `appVersion`
- `deviceHash`
- `userHash`
- `eventDate`
- `featureUsage`

## 如何保证“统计较准”

- 安装实例生成稳定 `installId`
- `deviceHash` 由 `installId + customerSalt` 计算
- `userHash` 由厂家提供的用户标识做单向哈希
- 服务端按天去重，按月汇总
- 客户续费时提供对账报表和席位趋势图

## 如何保证“厂家接入方便”

- 厂家只需要做三件事：
- 初始化 SDK
- 传 `customerId/appKey`
- 可选传 `userHash`

## 授权状态建议

- `ACTIVE`：可正常使用
- `GRACE`：欠费或续费中，进入宽限期
- `LIMITED`：仅允许基础功能
- `SUSPENDED`：授权暂停
- `EXPIRED`：授权到期

## 宽限期建议

- 默认 7 到 30 天宽限期
- 宽限期内继续允许基础输入和已授权能力
- 高成本云功能可优先限制

## 商业上最实用的落地建议

- 标准 SaaS OEM 客户：
- 在线 License
- 按设备或用户席位年付
- 每日心跳

- 集成成本最低版本：
- 厂家只传 `customerId + appKey + userHash`
- 其余都由 SDK 自动完成
