# 外部版-自动化授权配置

本文只说明第三方宿主在接入自动化套餐时，必须补齐的授权与发布动作。

当前自动化套餐基线：`Stellar v1.0.19(100190)`。本版本已包含被跳转快速授权、隐藏后台、无线调试快捷开启、开机预热模式、一次性跟随启动命令等官方能力。

## 什么时候需要看这页

- 只有客户购买或启用了自动化套餐时才需要执行本页
- 如果只接入输入法基础能力，可以跳过本页

## 步骤一：确认最终宿主包名

自动化授权不是按源码包名配置，而是按最终安装到设备上的宿主 `applicationId` 配置。

例如：

- release 包：`com.example.host`
- debug 包：`com.example.host.debug`

如果客户使用了 `applicationIdSuffix`，则必须以带后缀的最终包名为准。

## 步骤二：授予 WRITE_SECURE_SETTINGS

自动化快速启动链会尝试打开无线调试并连接本机 ADB，这一步要求宿主具备 `WRITE_SECURE_SETTINGS`。

如果没有这项权限，通常会出现下面的现象：

- 点击自动化开关后提示“自动化服务启动失败”
- 进入“输入法自动化引擎”后看到“服务未运行”
- “授权应用”页面为空白

调试阶段可通过 ADB 显式授予：

```powershell
adb shell pm grant com.example.host.debug android.permission.WRITE_SECURE_SETTINGS
```

说明：

- `debug` 和 `release` 如果包名不同，需要分别授权
- 更换宿主包名后，也要对新的最终包名重新授权

## 步骤三：在 Application 增加自动化初始化

```kotlin
class HostApp : Application() {
    override fun onCreate() {
        super.onCreate()

        OemHostRuntime.initialize(this, true)
    }
}
```

## 步骤四：在 Manifest 增加自动化元数据

```xml
<meta-data
    android:name="com.paopaoime.oem.enableAutomation"
    android:value="true" />
<meta-data
    android:name="com.paopaoime.oem.enableAutomationSettingsEntry"
    android:value="false" />
```

说明：

- `enableAutomation=true` 表示宿主显式声明需要自动化能力
- `enableAutomationSettingsEntry=false` 为默认基线：即使已集成自动化套餐，也不默认暴露“自动化设置”入口；仅企业明确需要时才改为 `true`
- 自动化权限元数据已随 SDK 默认合并，通常无需宿主额外暴露底层引擎键名

## 步骤五：按最终宿主包名重新发布输入法自动化引擎制品

这是自动化授权最容易漏掉的一步。

如果宿主包名发生变化，必须按新的宿主包名重新发布输入法自动化引擎相关制品，否则会出现下面这些问题：

- “输入法自动化引擎”页面能打开，但“授权应用”为空
- 页面显示“服务未运行”
- 手动启动后 Binder 仍然无法握手
- 默认授权仍然落在旧包名上

发布时至少要覆盖这两个参数：

```properties
automationEngineApplicationId=com.example.host.debug
automationEngineDefaultAllowedPackages=com.example.host.debug,com.example.host
```

这两个参数会影响：

- 自动化引擎 Provider Authority 的最终宿主包名
- native starter 传给 `ServerBootstrap` 的 `--manager-package`
- `ServerBootstrap` 写入的 `stellar.manager.applicationId`
- `StellarService` 启动后写入的宿主内部 `stellar = FLAG_GRANTED` 默认授权

如果只升级源码但没有按最终宿主包名重新发布制品，最常见现象就是服务进程已经启动，但页面停在“等待 Binder 响应”。

如果当前测试包名是 `com.paopaoime.company.debug`，则示例如下：

```powershell
.\gradlew.bat `
  publishReleasePublicationToOemLocalRepository `
  '-PautomationEngineApplicationId=com.paopaoime.company.debug' `
  '-PautomationEngineDefaultAllowedPackages=com.paopaoime.company.debug,com.paopaoime.company' `
  --no-daemon
```

## 步骤六：重新导出 SDK 并交付客户

输入法自动化引擎重新发布后，还要把新的制品重新导出到标准 SDK 目录，否则客户拿到的压缩包仍然是旧授权配置。

标准流程：

```powershell
cd OEM\SDK
.\export-sdk.ps1 -Clean -VersionTag 1.0.0.20260923
```

对客户交付的应该是新的 `oem-sdk-delivery-<version>.zip`，而不是仅口头告知配置项。

## 步骤七：Release/R8 保护检查

自动化引擎的 `stellar-server` 通过 `app_process` 启动，Release 包经过 R8 后必须保留服务入口类。

交付包中必须确认：

- `stellar-server-1.1.aar` 内包含 `proguard.txt`
- `proguard.txt` 包含 `-keep class roro.stellar.server.** { *; }`
- `proguard.txt` 包含 Android hidden API 相关 `-dontwarn`，例如 `android.app.ActivityThread`、`android.ddm.DdmHandleAppName`、`android.os.SELinux`

如果漏掉该保护，典型现象是：

- 点击自动化开关后一直停留在“正在启动自动化服务”
- “输入法自动化引擎”里显示服务未运行
- `logcat` 出现 `ClassNotFoundException: roro.stellar.server.bootstrap.ServerBootstrap`
- 当前宿主的 Stellar 内部授权无法落盘

## 步骤八：验收

最少完成以下验证：

1. 宿主安装后可以打开内嵌“输入法自动化引擎”
2. 宿主已具备 `WRITE_SECURE_SETTINGS`
3. 自动化引擎 Provider Authority 对应当前宿主包名
4. “授权应用”中能看到当前宿主包名
5. 启动服务后，重新进入输入法设置页仍能正常打开“自动化设置”
6. 如果第三方 App 跳转到输入法自动化引擎手动授权，来源 App 权限为“询问”时应弹出官方快速授权弹窗
7. 点击自动化开关后，`adb shell ps -A | findstr stellar` 能看到 `stellar_server`
8. `adb logcat` 中能看到 `Calling main entry roro.stellar.server.bootstrap.ServerBootstrap`，且不能出现 `ClassNotFoundException`
9. 输入法设置页自动化摘要显示已检测到可用自动化引擎服务，并提示当前输入法已获得授权
10. `adb logcat` 中 Binder 分发目标必须是最终宿主包名，不能出现回退到 `roro.stellar.manager` 或旧客户包名
11. 如使用无线调试或 su 回退启动，启动命令仍必须携带 `--manager-package=<最终宿主包名>`，不能只在普通 ADB 路径配置

## 结论

自动化套餐的关键不是单纯在宿主里打开一个开关，而是：

1. 宿主具备 `WRITE_SECURE_SETTINGS`
2. 宿主声明自动化能力
3. 宿主补齐自动化初始化链
4. 输入法自动化引擎制品按最终宿主包名重新发布
5. 重新导出并交付新的 SDK 压缩包
6. Release 包安装后完成 Stellar 服务启动、Binder ready 和内部授权验证

这些步骤缺任意一步，第三方宿主的自动化授权都可能失败。
