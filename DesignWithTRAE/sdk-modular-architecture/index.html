1现状问题分析（为什么现在做不到按模块交付）

问题现状证据影响
功能代码全部在 application 模块 AI回复（ime/ai、qa、compat/agent）、素材库（materialhub）、自动化（automation、midscene）、开发者（oem/debug）全部位于 app（com.android.application），无法产出 AAR 只能整包交付，无法按模块输出加固 AAR
交付是整仓 zip OEM/SDK/export-sdk.ps1 将 build/oem-sdk-repo 全量拷贝打包，无模块选择参数 客户拿到的永远是全量 SDK，无法按模块勾选下载
能力粒度与 5 大模块不对齐 OemCapability 仅 AI/AUTOMATION/UI 三档；OemFeatureToggles 仅 aiReply/materialLibrary/qaSession 三开关；开发者入口 meta 散落在 app 代码内 License、配置、文档三套口径无法按 5 大模块统一开通
已有可复用基础 oem-ime-sdk-core、aikeyboard-sdk-ai、oem-ime-host-bridge 已开启 R8 并发布到本地 Maven；OemImeSdk.initialize / License / Manifest 解析已收口 模块化只需“补齐拆分 + 交付选择 + 配置对齐”，不需推倒重来

2五大模块划分与代码目录映射

M1 基础+输入法 必选

  • oem-ime-sdk-core（OemImeSdk/License/Manifest解析/DrawerKit 公开 API）
  • oem-ime-host-bridge
  • ai-ime（fcitx5 内核 + host-bridge）
  • app/ime/** 内核部分：engine、service、keyboard、ui/settings、ui/setup、prefs、database、theme、libs、data
  • app/sdk/core/OemHostRuntime.kt、app/oem/OemEnterpriseConfig.kt

M2 AI回复 可选

  • aikeyboard-sdk-ai（AiKeyboardHostSdk 等）
  • app/ime/ai/**、app/qa/**
  • app/compat/agent/**、app/ime/knowledge/**
  • 原生依赖：paddleocr4android

M3 素材库 可选

  • app/materialhub/**（MaterialHubActivity / LaunchAuthorizer / logging）
  • ime/service 内 MaterialHubHostBridge、ToolbarActionHostBridge、MaterialHubLaunchRequest
  • 工具栏素材库入口（OemToolbarIconHelper 相关分支）

M4 Stellar自动化 可选

  • app/automation/**（bridge/stellar）
  • app/midscene/**（agent/automation/bridge/overlay/shizuku）
  • third_party/stellar/api/*（aidl/api/shared/provider/userservice/shizuku）
  • 可选 companion：stellar-manager

M5 开发者 可选

  • app/oem/debug/**（AI模型配置/会话存档覆盖/调试存储）
  • meta：com.paopaoime.oem.enable_developer_entry
说明：M1 是唯一必选模块，其余 4 个模块均依赖 M1；M2/M3 依赖 M1 的 UI 承载能力；M4 依赖 M1 + 高权限 companion；M5 仅调试期使用，正式交付默认关闭。

构建与发布流程

gradlew :模块:assembleRelease（R8）→ publishReleasePublicationToOemLocalRepository→ build/oem-sdk-repo（全量本地 Maven）→ export-sdk.ps1 -Modules core,ai,...→ oem-sdk-delivery-{tag}-{modules}.zip
  • 每个模块 AAR 输出时同步生成 MD5/SHA-256 写入 oem-sdk-manifest.json（用于完整性校验展示）。
  • 对外公开 API 统一收口到 com.paopaoime.aikeyboard.sdk.* 包，其余 internal 全部混淆。
  • app 继续作为 demo-app / 内部验证壳，不再作为对外交付物。

5模块化勾选交付方案

① 官网勾选模块（website/oem 下载页）→ ② 生成 oem-sdk-manifest.json（模块+版本+所需meta）→ ③ 导出组合 zip（仅含所选 AAR + 文档）→ ④ 客户按 manifest 集成并配置 meta

模块目录文件（单一事实源）：OEM/SDK/catalog/oem-sdk-catalog.json

字段说明示例（M3 素材库）
id / name模块 ID 与展示名material / 素材库模块
required / dependsOn必选标记与依赖模块required=false, dependsOn=["core"]
artifactsMaven 坐标列表com.paopaoime.oem:oem-ime-sdk-material:1.0.0
configKeys开通所需 Manifest metaenableMaterialLibrary / enableUi
capability / toggleLicense capability 与运行时开关UI + materialLibraryEnabled
docs随包文档外部版-SDK集成手册.md#素材库
官网勾选页基于 catalog 渲染（勾选框 + SDK 名称 + 包名 + MD5 + 版本文档链接）；导出脚本读取同一 catalog，保证“页面展示 = 实际交付”。

5.5抽屉开放层 DrawerKit（R9 新增）

在五大模块之上提供 UI 开放能力：内置抽屉可替换内容层、宿主可新建抽屉；开放层公开 API 收口于 M1（oem-ime-sdk-core），能力实现随 M2/M3 下发。

层级内容层归属配置方式鉴权 / R8 边界
L0 默认UISDK（AI回复 / 素材库现状界面）功能勾选开关（现状）随现状
L1 自定义UI宿主自绘（基座仅保留抽屉容器 + 返回/关闭头部）enableAiReplyCustomUi / enableMaterialLibraryCustomUi（默认 false）+ setDrawerContentFactory不新增鉴权；能力调用受既有企业开关约束
L2 自定义抽屉宿主自绘（空白基座交付，上限 4 个）registerCustomDrawer(id/标题/入口图标/内容工厂)无鉴权；宿主自研不纳入 SDK-R8

入口落位

  • 工具面板（宫格页）：自定义项按注册顺序追加到内置项之后，自动分页；
  • 顶部工具条：纳入「定制工具栏」排序/显示/隐藏体系（维持 6 个上限，已满进隐藏池），持久化 custom_<id>；
  • 入口图标由宿主提供（iconRes / Drawable 二选一），默认原色渲染不跟随内置 tint。

能力字段协议（UI 与能力解耦）

  • AI回复 12 字段：复制生成 / 极速生成 / 识屏回复 / 传图回复 / 截屏权限 / 相册选图 / 进度时间轴 / 结果列表 / 语气切换 / 重新生成 / 模型声明 / 受限态；
  • 素材库 11 字段：分类页签 / 文档子分类 / 搜索 / 素材列表 / 预设文件夹 / 发送 / 预览 / 悬浮添加 / 创作器 / 远程同步 / 状态位；
  • 字段经 OemImeSdk.aiReplyCapabilities() / materialCapabilities() 暴露，宿主可自由排版调用。
开放层公开 API（OemDrawerKit / Spec / 接口 / 字段常量）加入 oem-ime-sdk-core 的 proguard keep 与 consumer-rules；宿主自研代码位于宿主 APK，天然不纳入 SDK-R8 加密输入。

6配置体系模块化更新方案

层级现状更新为（按 5 大模块）
Manifest meta（OemManifestMetaKeys） enableAi / enableAutomation / enableUi / enableAiReply / enableMaterialLibrary / enableQaSession / enable_developer_entry（散落） 按模块归组：core（customerId/appKey/channel/environment/apiBaseUrl/enableUi）、ai（enableAi/enableAiReply/aiMode/aiOpenAi*/sessionArchiveMode/enableQaSession）、material（enableMaterialLibrary）、automation（enableAutomation + roro.stellar.permissions + manager 包名）、developer（enableDeveloper，收编散落 key）
运行时开关（OemFeatureToggles） aiReply / materialLibrary / qaSession 新增 automationEnabled / developerEnabled，与 meta 一一对应
能力位（OemCapability） AI / AUTOMATION / UI 扩展 MATERIAL_LIBRARY、DEVELOPER；License grantedCapabilities 按 5 模块下发
License featureFlags 粗粒度 capability 集合 与 catalog 模块 ID 对齐：["core","ai","material","automation","developer"]
交付 manifest 无 zip 内置 oem-sdk-manifest.json：所选模块、版本、MD5、所需 meta 模板（可直接粘贴进宿主 Manifest）

7实施路线图（三阶段）

阶段一：交付与配置模块化（不动大代码）

  • 新建 oem-sdk-catalog.json；export-sdk.ps1 增加 -Modules 组合导出与 MD5 manifest
  • website/oem 增加勾选下载页（本地静态，无外部依赖）
  • 配置对齐：OemFeatureToggles / OemCapability / meta keys 按 5 模块补齐（含 developer 收编）
  • 产出：可按组合导出的交付 zip + 模块化配置口径

阶段二：边界清晰模块物理拆分

  • 新建 oem-ime-sdk-material、oem-ime-sdk-developer、oem-ime-sdk-automation，从 app 迁入对应包
  • app 改为依赖新模块（demo-app 全量集成），OEM/company 按组合消费验证
  • 每模块独立 R8 + consumer-rules + 发布坐标，进入 catalog

阶段三：深耦合模块拆分与加固升级

  • AI 回复链（ime/ai、qa、compat/agent、knowledge）迁入 aikeyboard-sdk-ai
  • IME 内核（ime/**）与宿主壳分离，产出 ime-kernel 制品；BOM 上线
  • License/验签下沉 Native（沿用 02 方案第二层保护），依赖 AAR 全量混淆补齐

8风险与约束

  • app 单体拆分是最大成本：AI 回复与 IME service 深度耦合，阶段三只拆“桥接面”，不追求一次拆净。
  • 资源与 Manifest 合并：material/automation 含 Activity 与权限声明，AAR 化后需 consumer-rules + manifest placeholders 校验（先在 company 壳验证）。
  • stellar-manager 不入库：高权限 companion 保持独立 APK 交付，避免 SDK 包体积与权限面扩大。
  • 兼容承诺：旧整包交付保持可用；catalog 中 core 永远 required，老宿主不配置新 meta 时行为不变（默认值与现状一致）。
